## 2. Design and behavior

Use existing Fluent buttons, wrapping file actions, centralized pt-BR strings, native Windows picker/confirmation, controller queue and backend lane. Detect missing state by MissingFile issue as well as Missing status. Keep the missing row selectable. Put recovery before metadata/technical details; show the full old path. For existing files, keep file deletion visually distinct from list removal.

Disable catalog/file actions during read-only, disconnected, busy or administration transitions. A dirty selected inspector draft disables all three actions with readable guidance to save/discard first; apply the same removal guard to existing toolbar/context entry points. Preserve drafts on cancellation/failure and other rows' drafts. Disabled reasons remain keyboard discoverable.

**Locate:** add a single-selection native .ahk picker mode; the renderer supplies script identity/selection, never an arbitrary replacement path. Capture selection epoch, revision and old path before opening; cancel/closed document/changed selection/path/revision means no mutation. If the old path reappears while picking, reject stale recovery and refresh. Backend revalidates an existing canonical local .ahk, rejects duplicates case-insensitively, pending operations and ambiguous/running old or new targets, verifies loaded settings, and changes only Path on the same record. Preserve name, description, collection, manual keys, interpreter, privilege, launch-block/legacy provenance and startup intent; do not infer trust or recover an unrelated process. If RunAtLogin is true, explicitly reconfirm the new path's login behavior; cancellation leaves the old registration. This confirmation does not enable manager startup, register anything, or launch anything. Reanalysis follows successful Commit.

**Remove from list:** reuse existing native-confirmed remove flow, rename visible wording consistently, and state that the file and any execution remain untouched. Remove the row only on confirmed persistence.

**Delete file:** use `shell.trashItem` only in trusted main, behind a narrow injected native boundary for tests. Confirmation defaults to Cancel, names the exact canonical full path and says the file goes to the Lixeira and the list entry is removed. It clearly warns that Windows may ask for administrator permission if required. For a single verified running instance it also names the approved PID and explicitly says execution will be stopped first. Multiple, unknown, unverified, inaccessible, pending, externally conflicting or legacy-guarded identities are blocked with a reason.

Prepare a short-lived backend-bound file plan before confirmation. Bind script ID, current path, file fingerprint/identity, revision, selection and approved process identity; reject reuse or expiry. Revalidate after the dialog. If running, obtain/use the existing Stop plan with that exact approved identity under the combined confirmation. Require Stop=Confirmed plus complete fresh observation with no matching instance. A changed/reused PID, new instance, OnExit veto, access failure or timeout preserves file/catalog; never stop a replacement instance. If the approved instance has already exited, proceed only after complete observation proves no other matching instance. Cancellation after stopping preserves the stopped state.

After successful stop/no-running proof, authorize the file action in the backend lane: recheck settings fingerprint, authority, path/file identity, links/reparse components, process observation and pending guards; persist Pending before granting a single-use dispatch receipt. Main rechecks its file stamp/hash and path immediately before calling trashItem with the exact authorized backslash path. Do not accept directories, UNC, redirected or multiply linked files; never fall back to permanent deletion. Only the explicitly confirmed foreground Excluir arquivo action may call shell.trashItem and permit its Windows-native UAC prompt. Never initiate application runas/reopen, background/login/metadata UAC, or an automatic privilege workaround. If the user denies Windows permission or recycling fails after Stop, keep the catalog and clearly report that execution stopped but the file was preserved; do not restart or retry. If preservation itself is uncertain, report Unknown instead of claiming it.

Use existing OperationJournal with an appended RecycleFile operation value and dedicated recovery handling. Keep process operation enum values stable. Extend pending guards by canonical case-insensitive ScriptPath as well as ScriptId, so an unresolved recycle blocks target starts/relink/recycling, without blocking safe list removal or unrelated paths. Safe list removal must not clear that journal uncertainty: removing an entry and adding the same canonical path under a new ID still blocks start/relink/recycling until the original uncertainty is authoritatively resolved. Reuse the existing stored OperationRecord.ScriptPath; no new subsystem is needed. Record affirmative trash completion durably before attempting catalog removal. Only that affirmative receipt plus consistent current catalog/path state permits Commit removing the registration. Persisted receipt plus failed catalog save returns Partial and retains a missing row with clear guidance to remove it from the list after storage recovers; never trash again to retry catalog cleanup. An unexpected replacement file at the path is preserved and reported as Partial/Unknown rather than removed or guessed about.

## 3. Contracts and asynchronous outcomes

Add narrow typed relink and prepare/authorize/complete-recycle actions to existing validated request channels and source-generated JSON contexts. Only trusted main may submit a recycle receipt. Public preload methods accept selected registration context, not caller-selected deletion paths/tokens. Backend remains authoritative for record mutation, process policy, token consumption and durable outcomes. Completion reporting by the same operation ID is idempotent; effect dispatch is never replayed.

| State | Required meaning/recovery |
| --- | --- |
| Accepted | Plan prepared, not an effect or success; single-use plan expires after two minutes. |
| Pending | Durable authorization exists and dispatch may be underway. Block conflicting target operations. |
| Confirmed | Affirmative native trash receipt and catalog removal both persisted. |
| Partial | Stop already succeeded but later known failure, or native recycling succeeded while catalog/journal finalization failed. Clearly identify which happened. Do not restart or repeat trash. |
| Failed/cancelled | Known pre-dispatch failure/cancellation leaves the file/catalog; if Stop already happened, report that separately. |
| Unknown | Timeout, process/host loss after dispatch, missing receipt or inconsistent postconditions. Preserve registration, retain durable uncertainty and do not infer trash success from absence. |

Keep the existing five-second graceful-stop budget. Bound native-trash waiting at 30 seconds for UI reporting; a deadline cannot cancel an already dispatched native operation. Retain its late completion handler while the trusted host/session is alive; finalize only its same operation ID, independent of renderer survival. Backend request timeout keeps its existing uncertain-outcome semantics. On restart, Pending/Unknown recycling is not auto-dispatched and is not resolved by process absence. Surface it for manual Recycle Bin inspection/restoration and explicit safe list removal; an already durable affirmative receipt can explain cleanup without deleting another file. No delayed launch, restoration or destructive retry.

## 6. Material risks and assumptions

- Electron trash is path-based. Canonicalization, file-ID/hash checks and immediate revalidation reduce races but do not atomically pin the target across the last check and shell call; an external replacement/reparse change or external start can occur in that interval. Do not claim an atomic guarantee. Independent plan review must accept this documented boundary for the supported path API or pause only deletion for a stronger native design; relink/list removal remain separable.
- Stop and recycle are separate effects. A later cancellation/failure can leave the script stopped; disclose it, preserve metadata, and do not restart automatically.
- Recycling and catalog persistence are not one transaction. Durable receipts, Partial/Unknown reporting and no replay are required, including journal-save failures and late native completion.
- Journal enum extension must preserve existing numeric values; older installed binaries may reject newer operation records. Release/rollback review must account for data compatibility; do not silently rewrite the operational profile or erase uncertain records.
- Real native Recycle Bin behavior, elevated-host behavior and live visual results remain unverified at planning time. Tests must prove recoverability on owned fixtures; no permanent-delete fallback is acceptable. Root's official API verification is reused rather than re-collected.
